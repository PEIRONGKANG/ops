# 服务端媒体文件存储运行手册

## 范围与不可恢复风险

一期媒体文件写入应用服务器受控目录；生产根目录为 `/data/beverage-ops/media`，通过 `BEVERAGE_OPS_MEDIA_ROOT` 配置。PostgreSQL 只保存相对路径、哈希和不可覆盖的版本元数据，绝不保存绝对路径或二进制内容。

本期**不配置备份**，也**不接入病毒扫描服务**。服务器磁盘损坏、误删或恶意内容绕过白名单后的文件无法恢复；部署负责人必须确认接受此风险。类型白名单、大小限制、签名/容器校验、无宏 OOXML 校验、路径隔离和每请求鉴权仍然是强制控制措施。

## 部署前检查清单

1. 以运行后端进程的专用账户创建 `/data/beverage-ops/media`，目录所有者只允许该账户读写；目录权限建议为 `0700`。
2. 设置 `BEVERAGE_OPS_MEDIA_ROOT=/data/beverage-ops/media` 与 `BEVERAGE_OPS_MEDIA_PRODUCTION=true`。生产环境缺少根目录配置应拒绝启动。
3. 确认同一挂载点上可创建 `.staging/` 子目录，以保证暂存文件到正式路径可原子移动。
4. 由服务器运维负责磁盘空间、inode、目录权限及磁盘故障监控；应用不会做自动备份或容量扩容。
5. 确认 Nginx、Spring 静态资源、容器卷映射或其他 Web 服务均**没有**把该目录公开为 URL。只能通过 `/api/v1/evidence/{evidenceId}/files/current` 下载。
6. 配置并核对清理计划 `BEVERAGE_OPS_MEDIA_PURGE_CRON`（默认每天 02:00）；它只处理已替换或已撤回且已满三天的版本。

使用仓库的 Docker Compose 启动时，必须同时设置 `BEVERAGE_OPS_MEDIA_HOST_PATH=/data/beverage-ops/media`。该目录会以同一路径挂载进后端容器；Compose 已强制 `BEVERAGE_OPS_MEDIA_ROOT=/data/beverage-ops/media` 和生产模式，未设置主机目录时不会启动。主机目录必须持续保留，不能使用容器临时层。

## 文件限制与访问规则

| 类别 | 允许类型 | 最大大小 |
| --- | --- | ---: |
| 图片 | `.jpg`、`.jpeg`、`.png`、`.webp` | 50 MB |
| 文档 | `.pdf`、`.docx`、`.xlsx`、`.pptx` | 50 MB |
| 视频 | `.mp4`、`.webm`、`.mov` | 500 MB |

上传必须是 `OBJECT_REFERENCE` 证据的单个 Multipart 文件。后端生成相对路径，客户端不得提供服务器路径。读取、上传、替换、撤回均在每次请求依据证据所属班次和角色范围授权；视频读取支持单个 HTTP Range。写入、替换和撤回只允许处于执行中的班次，班次关闭后仅可授权读取和查询版本。

Spring Multipart 层允许单文件最大 500 MB、单请求最大 501 MB；图片和文档的 50 MB 限制由媒体类型校验进一步强制。部署时若由反向代理或网关接收请求，其请求体上限和超时必须不低于这一配置，否则合法视频会在到达应用前被拒绝。

Office Open XML 检查会拒绝宏、超过 10,000 个 ZIP 条目、解压总量超过 200 MB、压缩比超过 100:1 或单个关系文件超过 1 MB 的内容。媒体根、`.staging` 和其子目录不得包含符号链接；应用会拒绝发现的符号链接，但目录权限仍必须保持为运行账户独占，防止运行期间被篡改。

## 文件生命周期与清理

```text
CURRENT → REPLACED → PURGED
CURRENT → WITHDRAWN → PURGED
```

- 上传内容先写入 `${root}/.staging/*.part`，完成大小、哈希、签名和容器检查后才发布到正式位置。
- `CURRENT` 文件永不被定时清理，也不会因五年归档规则被本任务删除。
- 替换或撤回时，旧文件状态变为 `REPLACED` 或 `WITHDRAWN`，`purge_after` 为变更后三天。
- 到期后，定时任务只删除物理文件，随后把版本标记为 `PURGED`；文件名、SHA-256、原因、时间和审计记录长期保留。
- 已经缺失的物理文件标记为 `MISSING_ON_PURGE` 并正常转 `PURGED`。

## 中断与故障处置

### 暂存文件残留

上传中断或进程异常后，`.staging` 下可能留下 `.part` 文件；数据库不会指向它们。先确认没有正在执行的上传，再由运行账户删除创建时间早于 24 小时的 `.part` 文件。不要清空根目录，也不要删除 `evidence/` 下的当前文件。

应用在数据库事务最终回滚时会补偿删除刚发布的新文件；这不替代上述临时文件巡检。若宿主机在事务完成前断电，仍应依据数据库版本元数据与审计核对孤儿文件，且不得删除可被当前版本引用的内容。

### `DELETE_FAILED`

当清理任务无法删除历史文件时，版本仍保留 `REPLACED`/`WITHDRAWN` 状态，`purge_result=DELETE_FAILED`，任务会继续处理其他记录。检查目录权限、只读挂载、磁盘 I/O 和实际文件路径；修复后可等待下次计划任务重试。不得人工把 `CURRENT` 改为 `PURGED`，不得删除数据库版本元数据或审计记录。

### 文件找不到或无法下载

先核对版本状态与相对路径，确认调用者权限；若当前文件在磁盘上缺失，记录基础设施事故。由于本期无备份，无法从系统恢复二进制文件；保留元数据、哈希和审计用于追踪，并按业务流程重新上传新的证据版本。

## 五年归档边界

三天清理只适用于失效历史物理内容，不是五年归档或销毁机制。五年期满后的续存、转只读归档、导出位置和销毁审批仍是 DQ-07，尚未确定。
