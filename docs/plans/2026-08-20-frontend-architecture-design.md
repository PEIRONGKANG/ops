# 饮品生产性实训基地数字化运营系统前端架构与体验设计

**状态：** 已确认，待按实施计划开发  
**日期：** 2026-08-20  
**适用分支：** `renovate`  
**关联基线：** 产品需求文档、PRD 接口验收矩阵、认证基础设计、实时通知设计与服务端媒体存储设计。

## 1. 目标与范围

本设计定义全新 React 前端的产品体验和工程边界。它服务于饮品生产性实训基地的真实岗位运行、带教与治理，不复用、不迁移、不兼容旧 React、FastAPI、SQLite、PocketBase、单页原型或其业务数据。

首期交付四个内部角色各自完整、可直接调用 Spring 后端真实接口的工作台与页面骨架：

| 角色 | 首页目标 | 首期主导航 |
| --- | --- | --- |
| P3 实训学生 | 明确当前班次、待办和下一步动作 | 我的当班、我的日程、任务与证据、异常与交接、学习与成长、我的成果 |
| P2 运营经理 | 判断当日门店风险并完成现场处置 | 今日运营、排班定岗、签核中心、异常中心、运行记录 |
| T1 带教教师 | 观察、反馈、补训并跟踪学生成长 | 带教观察、反馈与补训、学生成长、课程筹备 |
| P1 教学督查 | 管理规则、人员与全局质量 | 运行总览、学期与人员、模板中心、课程与成果、归档与审计 |

外部评审入口和五年归档策略在产品需求中仍有待决项，且后端尚无对应端点；首期不在主导航中伪造入口。课程资料、课程任务和创意成果目前没有二进制附件 API，首期仅展示已有 JSON/引用数据，不显示不可用的上传按钮。

## 2. 体验与视觉方向

### 2.1 品牌表达

采用“清爽、专业的现代饮品品牌”方向。体验应令人感到门店运行可控、信息清晰、新鲜但不轻浮：用克制的茶绿和清透表面表达主品牌；用高对比排版、状态色和规律布局表达专业性。

- 默认明亮主题。暗色 Token 预留但不纳入首期验收，避免造成双主题质量不一致。
- 暖白与极浅雾灰构成背景层；面板以轻边界和表面色差分层，不使用厚重投影或玻璃拟态。
- 深茶绿/青绿色承载主操作、当前导航与成功反馈；柑橘橙承载待办与提醒；莓果红只用于阻断性异常和危险操作。
- 使用系统中文无衬线字体栈；时间、数值、班次编号采用等宽数字特性，便于现场快速扫读。
- 动效仅用于解释状态变化：150–220ms 的悬停、展开、上传与抽屉过渡；尊重 `prefers-reduced-motion`，不使用装饰性循环动画。

### 2.2 Material 3 实现决策

以 MUI 提供稳定的 React 无障碍与表单交互底座，并通过自定义主题、CSS variables 与封装组件落实 Material 3 的色彩、形状、层级和状态规范。MUI 不是最终视觉风格；业务代码只能使用项目的 Token 和封装组件，不允许散落的硬编码颜色、圆角、阴影或间距。

此方案相对于完全自建组件能在首期保障键盘操作、焦点管理、表格、表单与提示组件质量；相对于直接使用 Material Web Components 则有更成熟的 React 表单和数据密集型页面集成。

### 2.3 响应式与无障碍标准

- P3 采用小屏优先：44px 以上可触控目标、单列任务卡、底部导航突出“当班、任务、异常、我的”。
- P2/T1/P1 在桌面使用可收起的 Navigation Rail；窄屏转为顶部栏加抽屉，保留全部功能而非隐藏关键操作。
- 所有图标按钮必须有文字标签或无障碍名称；所有状态不用颜色作为唯一传达方式；表单错误必须与控件程序化关联。
- 页面在 200% 缩放、键盘顺序、屏幕阅读器标题层级和对比度方面符合 WCAG 2.2 AA 的可达目标。

## 3. 信息架构与页面模式

### 3.1 公共应用外壳

应用外壳包含品牌标志、当前角色工作台切换器、当前上下文（学期、门店、日期/班次）、通知中心和用户菜单。内容区保持稳定的标题、描述、主要操作与页面主体结构。

桌面端使用左侧导航轨道，宽屏时可展开文字标签；需要持续关注的现场状态或筛选条件可在右侧上下文面板呈现。移动端采用顶部栏和抽屉，P3 增加底部导航。角色决定默认导航与起始页；前端菜单可见性只改善体验，服务端仍是权限事实来源。

### 3.2 各角色首页

| 角色 | 首屏关键区块 | 可执行的高频操作 |
| --- | --- | --- |
| P3 | 今日班次、岗位与状态；待完成/退回任务；关键节点；反馈与补训 | 启动或进入任务、提交证据、上报异常、提交交接 |
| P2 | 门店/班次状态总览；待签核；阻断异常；待确认交接；缺失摘要 | 排班、进入班次、签核/退回、指派或验证异常 |
| T1 | 待观察学生；待反馈记录；待完成补训；成长与认证摘要 | 创建反馈、安排补训、查看学生过程档案 |
| P1 | 运行健康度；完成率/闭环率/证据完整率；待审批账号；模板与课程成果状态 | 管理学期人员、配置模板、查看审计与运行数据 |

### 3.3 可复用页面模式

- **列表页：** 标题、筛选、状态计数、主表格或卡片、分页与详情抽屉。桌面优先数据表格，小屏自动转为可扫读的卡片列表。
- **详情页：** 由摘要、状态时间线、核心业务内容、关联证据/反馈和审计摘要构成。审计信息不与日常操作争夺首屏，但始终可追溯。
- **当班执行页：** 任务、SOP、检查项、证据、异常与签核在同一工作区中按状态组织，避免要求 P3 在多个页面间往返。
- **表单页/抽屉：** 清晰展示必填项、权限限制、影响范围和提交后状态；危险或不可逆操作要求显示理由。
- **文件区：** 只突出当前证据版本；替换/撤回历史采用明确标签、时间和理由展示，不默认提供无意下载。

## 4. 前端工程架构

### 4.1 技术栈

| 范畴 | 选择 | 原因 |
| --- | --- | --- |
| 工程 | React 19、TypeScript、Vite | 现代前端构建与严格类型边界 |
| 路由 | React Router | 嵌套路由、鉴权门与角色工作台布局 |
| 组件 | MUI + 项目 M3 Token/封装层 | 可访问基础与品牌化视觉同时成立 |
| 服务端状态 | TanStack Query | 缓存、失效、重试、乐观更新和实时失效 |
| 表单 | React Hook Form + Zod | 可组合表单、声明式校验和类型化输入 |
| 表格 | TanStack Table；必要时以 MUI 容器呈现 | 服务端分页、筛选及响应式转换 |
| 实时 | `@stomp/stompjs` | 对接认证的 Spring STOMP `/ws` |
| 图标 | Material Symbols/统一图标封装 | 与 Material 3 语义和状态一致 |

工程位于 `apps/web`，不修改旧 `frontend` 或 `training_frontend` 目录。

### 4.2 目录边界

```text
apps/web/src/
  app/                 # 路由、Provider、主题、应用外壳
  features/            # 按业务领域划分的页面、查询、表单和组件
    auth/ governance/ operations/ learning/ assessment/ notifications/
  entities/            # 跨页面业务实体的只读展示和类型
  shared/
    api/               # 唯一 HTTP 客户端、领域 API、DTO、错误映射
    auth/              # 内存会话、权限与路由守卫
    realtime/          # STOMP 生命周期和事件到 Query key 的映射
    ui/                # M3 Token、封装组件、状态页、图标
    lib/               # 通用纯函数、日期和文件工具
```

页面、业务组件不可直接调用 `fetch`，不可读取环境变量来拼业务 URL，也不可把接口 DTO 作为表单内部状态长期泄漏。`shared/api` 是 API 调用、响应解析、错误标准化和请求头策略的唯一入口；feature 层负责把 DTO 转换成面向界面的 View Model。

## 5. 后端接口、认证与实时状态

### 5.1 契约原则

Spring 后端当前未发布 OpenAPI。本前端以现有控制器、集成测试和 PRD API 验收矩阵为唯一接口来源；每个已接入端点在领域 API 模块中定义请求、响应、枚举与分页类型。不得根据旧前端或旧数据库猜测字段。

首期调用的领域包括：

- 认证：`/api/v1/auth/login`、`change-password`、`me`、`refresh`、`logout`、`registrations`；
- 治理：`/api/v1/admin/*` 的学期、教学周、门店、团队、成员、模板、账号与审计能力；
- 运营：运营日、班次、岗位分配、任务、关键节点、证据、经营摘要、异常、交接，以及 P3/P2 仪表盘；
- 学习：资料、课程任务、创意成果、反思、反馈、补训、认证及个人成长视图；
- 评价：量规、成果包、评分记录、结果与个人成果/结果；
- 通知：列表、单条已读和全部已读。

### 5.2 会话模型

- 登录成功后，访问令牌仅保存在 JavaScript 内存；永不写入 LocalStorage、SessionStorage 或可被脚本读取的 Cookie。
- 后端以 HttpOnly `ops_rt` Cookie 保存刷新令牌。每次 API 请求使用 `credentials: 'include'` 并在有访问令牌时加 `Authorization: Bearer <token>`。
- 应用启动调用刷新端点后请求 `/auth/me` 以恢复会话。多个请求同时收到 401 时实施单飞刷新，其余请求等待刷新结果并至多重放一次。
- 刷新失败会清空内存会话、断开 WebSocket，跳转登录页并保存原目标地址；登录成功后安全返回。
- 角色切换只改变前端工作台上下文和路由，绝不假定权限已改变；每次服务端拒绝仍按真实权限处理。

### 5.3 查询、变更与失败状态

TanStack Query 统一管理服务端缓存。写操作成功时仅失效与该对象有关的详情、列表、待办和工作台 query，而不是全页刷新。网络离线、加载、空结果、权限不足、服务端业务拒绝、不可恢复错误和版本冲突均为独立、清晰的 UI 状态。

当后端报告版本冲突时，界面提示“该记录已被其他人更新”，说明本次更改未被覆盖，提供重新加载后继续编辑的入口。普通删除或撤回操作必须展示影响与理由，不能用隐式成功遮蔽审计事实。

### 5.4 实时事件

登录且获得访问令牌后，客户端连接 Spring STOMP `/ws`，只订阅当前身份允许的个人 `/user/queue/operations`。事件不会直接修改未知结构的缓存，而是映射到明确的 Query key 并请求最新事实。断开后以指数退避重连，在顶部显示非阻断的连接状态。退出、令牌失效或角色会话销毁时必须断开连接。

### 5.5 证据媒体

运营证据真实调用：上传、列表、当前文件、替换、撤回和授权下载端点。上传采用 `multipart/form-data`，前端只接受后端明确允许的 JPEG/JPG、PNG、WebP、PDF、DOCX、XLSX、PPTX、MP4、WebM 与 MOV；预检不能取代后端校验。页面显示上传进度、文件大小/类型提示、失败重试、当前版本及近三日的已替换/已撤回历史状态。

浏览器下载必须请求后端授权下载端点，前端不拼接服务器文件路径。课程资料和创意成果附件的服务端二进制能力尚未完成，因此不显示真实附件上传控件。

## 6. 质量门槛与验收

### 6.1 Good Design 原则

- 首屏让每个角色知道“现在最重要的一件事”，不以大屏数据装饰取代操作。
- 状态、责任人、时间、风险与下一步动作在同一视觉层级可快速定位。
- 每次提交都给出明确成功、失败或待确认反馈；不可静默改变业务状态。
- 信息密度按任务而非按组件平均分配：P2/P1 可高密度浏览，P3 的现场执行维持低认知负担。
- 关键动作、异常和签核的语义在四个工作台一致；界面不会用颜色、图标或文案表达相互矛盾的状态。

### 6.2 工程验收

1. 未登录用户无法访问业务路由；登录、刷新、退出与 401 单飞恢复符合后端 Cookie/Bearer 模型。
2. P1/P2/P3/T1 分别看到匹配的首页和导航，且访问无权路由显示权限页而不是空白页。
3. 每个已接入业务模块通过真实 Spring API 获取数据，页面没有模拟成功数据或旧系统适配代码。
4. P3 可从工作台进入本人班次、任务和证据流程；P2 可从今日运营进入签核、异常与交接；T1/P1 可访问各自被授予的学习/治理页面。
5. 上传、替换、撤回运营证据正确处理进度、权限、失败和历史版本展示；无文件路径泄漏。
6. WebSocket 重连与事件触发关联 Query 刷新；断线不会阻塞日常 REST 操作。
7. 关键页面在窄屏和宽屏可用；核心表单可用键盘完成，文本/状态对比度达到 AA 目标。

## 7. 明确不做与待决项

- 不做旧系统登录、数据迁移、双写、旧接口适配或以旧页面为基础的视觉复刻。
- 不做 POS、订单、采购和库存流水 UI；仅显示后端提供的外部经营摘要。
- 不做外部评审门户、五年归档操作 UI、课程附件二进制上传，直到后端契约和业务待决项获得确认。
- 不在前端固化正式认证阈值、补训时限和评分权重；它们必须由 P1 模板/量规 API 提供。
- 首期不接入 Spring AI 供应商或生成式 AI 交互。
