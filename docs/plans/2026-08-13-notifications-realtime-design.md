# 通知、运营工作台与授权实时事件设计

**状态：** 已确认，实施中
**关联 PRD：** `docs/plans/2026-08-02-beverage-training-operations-system-design.md` 第 5.8、6、8.3、9 节；交付计划 Task 5。

## 决策

采用“PostgreSQL 站内通知 + 事务后应用事件 + 认证 STOMP WebSocket”的组合：

- 站内通知是业务待办的持久事实，供重连、移动端和未在线用户查询；通知不删除，只更新已读状态。
- 业务用例在写入成功后发布领域应用事件；监听器在事务提交后创建通知并向已授权的个人目标发送轻量实时刷新事件。失败或回滚的写入不得产生通知或实时事件。
- WebSocket 仅提供 `/user/queue/operations` 个人队列。客户端不携带班次、门店或学期主题，也不能订阅任意业务 ID；握手使用已有 Bearer access token，服务端从当前身份派生用户队列。
- P3 工作台由服务端按账号聚合个人班次、未完成/退回任务、待确认交接和未读通知；P2 “今日运营”由服务端按已授予的学期+门店范围聚合待排班、待关键签核、阻塞异常、待确认交接和待补充经营摘要。

## 替代方案与取舍

1. **仅 REST 轮询**：实现简单，但无法满足 PRD 的自动刷新目标，且会把轮询和待办推断逻辑转移到前端。
2. **开放式按班次/门店 STOMP 主题**：即时性好，但客户端可猜测或篡改主题，授权边界难以保证。
3. **已选择：持久通知 + 服务端派生个人 STOMP 队列**：保持待办可恢复、实时状态可推送，并避免将资源范围授权交给客户端。

## 数据与接口边界

- 新建 `shared_notifications`，记录 `recipient_account_id`、事件类型、资源类型/UUID、标题、内容、已读时间、创建时间；不保存旧系统 ID、POS 明细或对象二进制数据。
- `GET /api/v1/notifications` 只返回当前用户通知；`POST /api/v1/notifications/{id}/read` 只允许收件人标记已读；`POST /api/v1/notifications/read-all` 仅处理当前用户。
- `GET /api/v1/me/operations-dashboard` 只返回当前 P3 账号可操作的个人项目；`GET /api/v1/operations/today` 只返回当前 P2/P1 获授权门店范围的今日风险和待办。
- 不实现公开主题、任意资源订阅、旧数据同步或旧系统通知兼容接口。

## 事件和收件人

| 业务事件 | 收件人 | 通知/工作台效果 |
| --- | --- | --- |
| 岗位分配或调整 | 被分配 P3 | 当班或岗位变更待办 |
| 任务或关键节点被退回 | 原提交 P3 | 补充证据/重新提交待办 |
| 异常被指派 | 指定处置人 | 异常处置待办 |
| 交接已提交或被退回 | 指定接收 P3 / 发起 P3 | 接收或补充待办 |
| 经营摘要待补充 | 原采集 P3 | 外部数据补充待办 |

## 安全、错误与测试

- STOMP 握手沿用 token 解析与会话有效性检查；不存在或过期 token 拒绝连接。
- WebSocket 的订阅拦截器仅允许认证用户订阅自己的 `/user/queue/operations` 队列；禁止 `/topic/**`、其他用户队列和客户端声明的资源主题。
- 通知读取使用收件人条件更新，跨账号请求统一返回 `FORBIDDEN`；仪表盘查询不接受可用于扩大范围的 accountId、termId 或 storeId。
- 集成测试覆盖通知收件人、个人/门店范围隔离、已读版本行为、事务回滚不推送，以及 STOMP 订阅授权。
